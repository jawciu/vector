## Feature 1: AI Insights

### Three-layer architecture

**Layer 1 — Data (deterministic JS, no AI).** [lib/db.js](lib/db.js) queries + [lib/ai/context.js](lib/ai/context.js) compute facts (`tasksOverdue`, `tasksBlocked`, `tasksBlockingOthers`, `daysToTargetGoLive`, `velocity7d`, `phaseState`, `customerEngagement`, `bouncedContacts`, plus `health` / `healthReasons` from existing [lib/health.js](lib/health.js)). Output: a 2–5KB JSON snapshot.

**Layer 2 — Reasoning (Claude streaming).** One API call: cached system prompt + snapshot user message → structured JSON via `output_config.format`. ~5–10 seconds total.

**Layer 3 — Storage & display.** Save to `Insight` table with a context hash. Stream tokens to the browser via SSE. Subsequent loads read cached payload instantly.

### Data flow

1. Page renders → server component fetches latest `Insight` for this scope
2. Compute current `contextHash` from a Layer 1 snapshot
3. If cached `contextHash` matches **and** generated <4 hours ago → render cached
4. Otherwise → render stale (or skeleton if none) + client triggers `POST /api/insights/[scope]/[id]`
5. Edge route streams Claude's response to the browser; on completion, writes new `Insight` row + `AICall` log row

### What Layer 1 produces vs what AI produces

| Field | Generated by | How |
|---|---|---|
| `headline`, `tldr`, `trend` | AI | Pure narrative interpretation |
| `focusToday[]` | AI fed by Layer 1 signals | Layer 1 surfaces overdue / blocked / blocking-others tasks; AI picks the 2–3 that matter most today |
| `focusThisWeek[]` | AI fed by Layer 1 signals | Layer 1 surfaces phase target dates, days-to-go-live, velocity, engagement; AI does strategic interpretation |
| `risks[]` | AI with strict citation rule | Must cite specific data points; "could be a problem later" not allowed |
| `wins[]` | AI scanning recent activity | Last 7 days only |
| `nudges[]` | Layer 1 detects, AI ranks/rephrases | Mechanical detection; AI picks top 2–3 |

### Insight payload schema

Same shape at both scopes (per-onboarding and portfolio); items reference `taskId` / `onboardingId` accordingly.

```json
{
  "headline": "Acme is on track but customer engagement is dropping",
  "tldr": "Phase 1 done, but legal pack overdue and customer hasn't logged in for 12 days.",
  "focusToday": [
    { "taskId": 42, "reason": "3 days overdue and blocking customer review" }
  ],
  "focusThisWeek": [
    { "summary": "Prep go-live data review by Thursday — currently no slot booked" }
  ],
  "risks": [
    { "severity": "high",
      "summary": "Customer hasn't logged into the portal for 12 days",
      "evidence": ["Contact.lastSeenPortalAt", "magic link expires in 5 days"] }
  ],
  "wins": [
    { "summary": "Phase 1 completed on schedule (8/8 tasks done)" }
  ],
  "nudges": [
    { "kind": "unassigned_task", "taskId": 67, "summary": "No owner set on 'Send DPA' — 4 days old" },
    { "kind": "follow_up", "taskId": 51, "summary": "Blocked 6 days waiting on customer — draft a nudge?", "ctaTarget": "draft_followup" }
  ],
  "trend": "stable"
}
```

### Nudge kinds (Layer 1 detection)

| Kind | Detection rule | CTA |
|---|---|---|
| `unassigned_task` | No `ownerId` and no `assigneeContactId`, age > 2 days | Open task drawer |
| `follow_up` | Blocked >5 days OR overdue >3 days with customer assignee | Existing Draft Follow-up flow (PLAN.md §3.1) |
| `stale_task` | No status change in 14 days | Open task drawer |
| `customer_dark` | `Contact.lastSeenPortalAt` >10 days ago, magic link still active | Existing follow-up flow |

### Phase state classification (Layer 1)

Replaces brittle "% done". Computed per phase.

| Status | Rule |
|---|---|
| `complete` | `Phase.isComplete = true` (manual flag — ground truth) |
| `blocked` | Has any tasks with `status = Blocked` |
| `stalled` | No task status changes in 7+ days AND has open tasks |
| `progressing` | At least one task moved forward in last 7 days |
| `not_started` | All tasks "Not started" |

### Freshness model

| Layer | Freshness |
|---|---|
| Layer 1 (numbers, badges) | Always live — fresh DB query on every page load |
| Layer 2 (AI narrative) | Cached. Invalidated by context hash mismatch OR after 4 hours OR by manual "Regenerate" button |

Hash inputs: task IDs + statuses + due dates, blocked relationships, customer engagement flags, phase states. Description edits, sort/filter changes, and added comments do **not** trigger regeneration.

### System prompt (Insights)

```
You are Vector, an AI assistant inside an onboarding workflow tool used
by B2B vendors to manage customer onboardings. Your job is to help the
vendor (Caroline and her team) understand the state of an onboarding at
a glance and decide what to focus on today and this week.

You will receive a JSON snapshot of one onboarding (or a portfolio).
Produce a structured summary in the schema provided.

RULES — non-negotiable:
1. NEVER invent facts. Every claim must reference a specific taskId,
   onboardingId, or named field from the snapshot.
2. Every action item in `focusToday` MUST cite a specific taskId
   (or onboardingId at portfolio scope).
3. "Risk" means concrete evidence something will go wrong.
   "Could become a problem later" with no evidence = NOT a risk.
4. "Win" means something objectively went well in the last 7 days.
5. `focusThisWeek` is for strategic priorities, not today's micro-actions.
6. `nudges[]` items are pre-detected by our system — RANK (pick the 2–3
   most important) and REPHRASE (in Vector's voice). Do not invent nudges.
7. If signal is low (new onboarding, quiet week), say so — do not pad.
8. Tone: clear, direct, slightly punchy. No corporate filler.
9. Length caps:
   - headline: 80 chars · tldr: 200 chars
   - focusToday[].reason: 120 chars
   - focusThisWeek[].summary: 140 chars
   - risks[].summary: 140 chars

Today is {{TODAY}}.
```

### Where it surfaces

- **[app/page.js](app/page.js)** → home dashboard. Hero card streams portfolio headline + TLDR. Table sorted below.
- **[app/onboardings/[id]/OnboardingDetailClient.js](app/onboardings/[id]/OnboardingDetailClient.js)** → Insights default tab. Hero with headline + TLDR; cards for Focus today / Focus this week / Risks / Wins / Nudges.

- Per-onboarding generation: ~$0.015
- Portfolio (10 onboardings, aggregated): ~$0.03
- Portfolio project with on-demand regeneration only: **<$5/month total**

## Feature 2: Auto-task organisation

### Ingestion: webhooks only

| Source | Mechanism | Live? |
|---|---|---|
| Miniti | Webhook (token query param auth, no HMAC per Ian's spec) | ✓ |
| Linear | Webhook (signed, first-class support) | not yet |
| Attio | Webhook for record changes | not yet |

Each webhook handler: verify auth → write `ExternalEvent` row → trigger orchestrator via `after()` → return 200 fast.

### Transcript processing pipeline (Miniti)

```
1. Webhook fires → ExternalEvent row written, return 200
2. Match transcript → onboarding (heuristics, no AI):
     a. attendees[].domain → Company.domain
     b. attendees[].email → Contact.email
     c. Title fuzzy match → significant-word match against Company.name
     d. Content fuzzy match → search summary/topics/notes/transcript for company name
     e. Ambiguous (0 matches OR multiple) → matchAmbiguous=true, surfaces in inbox
3. Load context: open tasks, recent closed tasks, contacts, phases
4. Single Claude call with tool use:
     - System prompt (transcript-specific)
     - Miniti's pre-extracted action_items[] + existing tasks list + email lists + today's date
     - Tool surface (below)
5. Each tool call → PendingAIChange row with sourceQuote + confidence.
   Mark ExternalEvent.processedAt = now
6. Caroline reviews drafts in "Vector suggests" inbox at /ai-drafts
```

### Tool surface for the orchestrator

```
create_task_draft({ title, description, owner: "vendor"|"customer",
  dueDate, phaseId, priority, sourceQuote, confidence })

match_to_existing_task_draft({ taskId, sourceQuote,
  action: "comment_only" | "reassign" | "reprioritise" | "update_due_date",
  payload })

update_task_status_draft({ taskId, newStatus, sourceQuote, confidence })

flag_no_action_items({ reason })
```

### System prompt (transcripts)

```
You are Vector. You process meeting transcripts from B2B customer
onboardings and propose task drafts that the vendor reviews before
applying.

You will receive: the full transcript, existing OPEN tasks for this
onboarding, vendor team emails, customer team emails, today's date.

For each concrete action item, emit ONE tool call.

Rules — non-negotiable:
1. Only firm commitments. "We'll send X by Friday" → action.
   "We should think about X" → NOT an action.
2. Match before you create. If an action item maps to an existing open
   task, use match_to_existing_task_draft. Don't duplicate.
3. If someone reports completing existing work, use update_task_status_draft.
4. Every tool call MUST include sourceQuote — exact transcript snippet
   (1–3 sentences) that justifies the action.
5. Owner attribution: if speaker is on vendor team → "vendor"-owned;
   if customer team → "customer"-owned.
6. Confidence:
   - high = explicit + named owner + clear deadline
   - medium = clear commitment, vague timing
   - low = implied or ambiguous
7. If the transcript has no concrete action items, call flag_no_action_items.

Today is {{TODAY}}.
```

### Match heuristic (current implementation)

Lives in [lib/integrations/miniti.js](lib/integrations/miniti.js) `matchMeetingToOnboarding`. Steps run in order, stopping at first single-onboarding match:

1. **Domain** — unique attendee domains compared to `Company.domain` (lowercase, exact). Strongest signal.
2. **Email** — attendee emails looked up against `Contact.email` rows.
3. **Title (significant words)** — for each company, extract significant words (length ≥ 2, not in stopword list `co/inc/ltd/llc/corp/company/the/and/of/for`) and check if any appears with word boundaries in `meeting.title`. So "Acme Co" matches "Acme weekly sync" via the "Acme" token.
4. **Content (significant words)** — same significant-word match against `summary + topics + notes + transcript`. Catches meetings where the title is generic but the customer name appears in the body.
5. **Ambiguous** — 0 matches OR multiple matches → `matchAmbiguous=true`, surfaces in `/ai-drafts` "Needs your input" for manual assignment.

### Linear and Attio events (when shipped)

Same orchestrator function, smaller context payload:
- **Linear** "issue Done" → typically one `update_task_status_draft` or `match_to_existing_task_draft`
- **Attio** "deal stage changed" → typically zero or one tool calls; CRM events tend to *prioritise* existing tasks rather than create new ones

### "Vector suggests" inbox UX

Lives at `/ai-drafts`, link in left sidebar. Two sections:

1. **"Needs your input"** (yellow-bordered cards) — events with `matchAmbiguous=true`. Onboarding picker dropdown + "Assign + process" button. Assignment kicks off the orchestrator.
2. **"Suggestions"** — pending `PendingAIChange` rows. Each card shows action + source quote + confidence pill + Approve/Reject buttons.

**Approve** → `POST /api/ai-drafts/[id]/approve` → switch on `action` and call existing `createTask` / `updateTask`. Marks draft `applied`, sets `appliedTaskId`. ActivityLog row written automatically.

**Reject** → `POST /api/ai-drafts/[id]/reject` with optional reason. Used as training data later.

**Edit-then-approve** → backend accepts `overrides` body on approve. UI form not yet built (in polish backlog).

`ActivityLog.actorType` extension to accept `"ai"` was scoped but not implemented — `PendingAIChange` itself serves as the AI-provenance audit trail today.

### The 10-second Vercel Hobby ceiling

- Webhook handlers run on Node runtime → 10s function lifetime cap.
- We use Next 16's `after()` to run the orchestrator after the 200 ack — extends the function lifetime up to the cap, but doesn't bypass it.
- Long Sonnet calls can exceed 10s. Stuck events surface in `/admin/ai` with a Reprocess button; second runs are usually faster because of prompt caching.

## Miniti webhook — Ian's authoritative spec

Confirmed by Ian on 2026-04-28. Source of truth for the webhook receiver. Schema lives in `WebhookService.swift`, locked by `WebhookPayloadTests.swift` on Miniti's side.

### Transport

- **Method**: `POST application/json`
- **Timeout**: 10s, fire-and-forget. **No retries, no signing header.**
- **Receiver requirements**: idempotent on `meeting.id`; treat the endpoint as unauthenticated → use a hard-to-guess URL OR a token query param.
- **Configured by user** in macOS/iOS Settings → Webhook URL.

### Our auth choice

Token query param: `POST /api/integrations/miniti/webhook?token={MINITI_WEBHOOK_TOKEN}`. The token lives in env as `MINITI_WEBHOOK_TOKEN`; Caroline pastes the full URL (with token) into Miniti's Settings.

### Events

| Event | Fires when |
|---|---|
| `meeting.saved` | User ends/leaves a meeting |
| `meeting.updated` | Insights regenerate on a persisted meeting (e.g. re-run from history) |

Same payload schema; switch on `event` in the handler. We process both — `meeting.updated` may bring richer `action_items` than the initial save.

### Payload — full shape


### Field rules

**Always present**: `event`, `meeting.id`, `title`, `date`, `duration_seconds`, `language`, `action_items`, `key_decisions`, `topics`, `discussion_flow`, `notes`, `speaker_count`, `transcript`.

**Nullable / omitted entirely when empty** (don't assume the key exists): `summary`, `end_time`, `meddpicc`, `training`, `questions`, `speaker_names`, `calendar_event_id`, `attendees`.

**Important gotchas**:
- `transcript[].timestamp` is **seconds** from meeting start, not ms.
- `transcript[].speaker` is the resolved label — user's mapped name, `"You"` for the local mic, or `"Speaker N"` fallback. The raw integer speaker ID is the *key* in `speaker_names` (`-1` is the local mic).
- `attendees` may be **entirely absent** when the meeting was started without a calendar event. The match heuristic must handle the no-attendees case.
- `training.speakers[].is_you` is the cleanest vendor/customer split signal — better than parsing names.
- `meddpicc` is omitted entirely when every field is empty — don't `meeting.meddpicc.metrics` without a guard.

### Delivery semantics — what we adapt to

- **Idempotency**: enforced by `@@unique([source, sourceId])` on `ExternalEvent`. Duplicate `meeting.id` deliveries are silently absorbed.
- **No retries from Miniti**: app downtime loses events. Mitigation: `meeting.updated` events fire on regenerate, giving a natural backstop. For critical missed events, manually re-save from Miniti history.
- **Fire fast**: ack within ~50ms (write `ExternalEvent`, return 200). Orchestrator runs async after the response via `after()`.
