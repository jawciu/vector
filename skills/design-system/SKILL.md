# Design System Skill

The canonical source of truth for this project's design system is [DESIGN.md](../../../DESIGN.md) at the project root. **Read it first** when working on UI — it has tokens, component rules, hover patterns, and do's and don'ts in one place.

## What's in DESIGN.md

- **YAML front matter** — every design token (colors, typography, spacing, rounded, shadows) in machine-readable form. Lints against the design.md spec via `npm run lint:ds`.
- **Markdown body** — Overview, Colors, Typography, Layout, Elevation, Shapes, Components, Do's and Don'ts. The reasoning that the YAML alone doesn't capture.

## Build pipeline

- DESIGN.md is the source. Editing it is what changes the design system.
- `app/theme.css` is autogenerated from DESIGN.md by `scripts/build-theme.js` — **never edit theme.css directly**.
- `npm run build:ds` regenerates the CSS variables. `predev` and `prebuild` run it automatically.
- `npm run lint:ds` validates structural correctness (contrast, broken refs, schema).

## When working on UI

1. Read DESIGN.md first
2. Reuse existing primitives in `app/ui/` (Button, IconButton, TabBar, Tooltip, FieldPill, FieldRow, CalendarDropdown, Icons)
3. Use `MenuList` + `MenuOption` from `app/components/Menu.js` for any dropdown / popover
4. Reference colors via `var(--token-name)` — token names are kebab-case (`--bg-elevated`, `--action-hover`, etc.)
5. If you need a new token, edit DESIGN.md (not theme.css), then run `npm run build:ds`

## When extracting a new DS primitive

- DS primitives go in `app/ui/`, not `app/components/`
- Only extract when Caroline asks — incremental adoption, no premature abstraction
- After extracting, document the component in DESIGN.md's Components section
